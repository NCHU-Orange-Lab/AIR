# AIR 規範說明

這份文件說明規則、檢查機制、設定檔與維護方法。給使用者與 AI 參考；AI 平常不需要讀它，只在需要查詢時才讀。

---

## 1. 分層

依賴方向由上往下；同一列的層互不依賴。各層都是套件（`.air/project.toml` 的 package-dir）底下的子套件。

```
main/                          組裝：載入 → 執行 flow → 儲存
flows/ │ adapters/ │ storage/  串接步驟 │ 包裝第三方工具 │ 所有讀寫
steps/                         純邏輯
contracts/                     跨層的型別（types.py）與介面（ports.py）
```

| 層 | 純的層 | 內部可以 import | 外部可以 import |
|---|---|---|---|
| contracts | 是 | contracts | 白名單 |
| steps | 是 | steps、`contracts.types` | 白名單 |
| flows | 是 | steps、flows、contracts | 白名單 |
| adapters | 否 | contracts | 任何套件 |
| storage | 否 | contracts | 任何套件 |
| main | 否 | 全部 | 任何套件 |

- **白名單**：標準庫的純計算模組（typing、dataclasses、collections、itertools、functools、math、statistics、decimal、re、json、datetime 等）、pandas、numpy，以及專案在 `.air/project.toml` 的 `imports.extra` 加入的模組。
- **純的層**另外還會檢查：I/O、`print`、讀時間、取亂數。
- **只有 flows 會呼叫 Protocol**：adapter 實作 `contracts/ports.py` 的 Protocol → main 建立 adapter 並注入 flow → flow 呼叫它，再把結果（資料）交給 steps。
- **舊程式碼**：套件內還沒搬進任何層的模組。不受檢查；但層不能 import 舊程式碼，遷移期間可以經使用者同意，在 `migration.allow-legacy` 暫時允許。

## 2. 規則從哪裡來、何時送到 AI 面前

| 時機 | 機制 | 內容 |
|---|---|---|
| 每次對話 | 專案的 `AGENTS.md` 放著 `AIR/AGENTS.md` 的全文；`CLAUDE.md` 匯入它（使用者原有的 `CLAUDE.md` 則匯入 `AIR/AGENTS.md`） | 架構、前綴對照、3 條常駐規則 |
| session 開始、壓縮後 | hook：附上目前狀態（階段、違規數、現在該做的事） | `status` 的內容 |
| 進入某一層 | hook：第一次讀或改某一層的檔案時附上 `AIR/rules/<層>.md`（同一個 session 只附一次；壓縮後重新附） | 該層的規則（每層最多 6 條） |
| 做某種任務 | skill（`.claude/skills/air-*`、`.agents/skills/air-*`） | 做法與判斷標準 |
| 違規當下 | 檢查訊息帶規則編號與修法 | 被違反的那條規則 |

規則前綴：`CTR`→contracts、`STEP`→steps、`FLOW`→flows、`ADP`→adapters、`IO`→storage、`MAIN`→main、`TEST`→tests。完整內容在 `AIR/rules/`。

規則標記：〔hook 檢查〕所有違反方式都會被抓到；〔hook 部分檢查〕只抓得到部分寫法（規則中會舉出抓不到的例子）；沒有標記的完全靠自律。

## 3. 檢查

### 關卡

| 關卡 | 何時 | 範圍 | 違規時 |
|---|---|---|---|
| pre-edit hook | 每次用編輯工具改檔前 | 該檔案的路徑 | 擋下受保護路徑（`AIR/`、hook 設定、`.git/`、AIR 複製的 skill）與分析／計畫階段對 `.py` 的修改；`.air/project.toml` 改成請使用者確認（Codex 沒有確認機制，改成提醒） |
| post-edit hook | 每次編輯 `.py` 後 | 該檔案 | 回報（修改已寫入，必須修正） |
| pre-bash hook | 每次執行 Bash 前 | 該指令 | 擋下略過 commit 前檢查的指令 |
| stop hook | AI 要結束前 | 所有層 | 要求繼續修正（只提醒一次） |
| commit 前檢查 | 每次 `git commit` | 所有層 | commit 失敗 |
| `verify` | 每批遷移結束、收尾時（由 AI 執行） | 所有層＋專案的測試指令 | 驗收未通過；沒有通過的紀錄就不能進入 `done` |

用 Bash 改檔不會觸發 post-edit，所以由 stop hook 補檢查。commit 前的檢查可以被人手動略過，目前沒有無法略過的關卡（需要 CI 加上分支保護）。

### 宿主

規則、檢查與 skill 不分宿主；宿主的差異集中在 `AIR/lib/airkit/hosts.py`：hook 設定寫在哪、skill 裝在哪、怎麼找專案根目錄、payload 的欄位名稱、聽不聽得懂 `ask`。

| 宿主 | hook 設定 | skills | 差異 |
|---|---|---|---|
| Claude Code（Grok Build 讀同一份設定，`stopHookActive` 等欄位名稱的差異在 `hosts.parse()` 處理） | `.claude/settings.json` | `.claude/skills/` | 六個 hook（session 開始、讀檔前、編輯前、編輯後、執行 Bash 前、結束前） |
| Codex | `.codex/hooks.json` | `.agents/skills/` | 五個 hook（沒有 Read 工具，規則在第一次編輯該層時附上）；PreToolUse 不支援 `ask`，改成提醒；hook 要在 Codex 裡信任過才會執行；用 `git rev-parse --show-toplevel` 找根目錄 |

安裝時預設裝所有宿主（`--host` 可以只裝一種），`.air/hosts` 記錄這台電腦裝了哪些；AIR009 的接點檢查只要求裝過的宿主。`python3 AIR/air.py doctor` 列出每個宿主的接線狀態（hook 齊不齊、是不是舊格式、skill 是不是目前版本），只讀不修。

### `check` 與 `verify`

`check` 是快速診斷，結果分四種：**通過**、**違規**、**沒有檢查任何檔案**（各層目錄都不存在；結束碼 0，但不代表合規）、**輸入錯誤**（指定的檔案不存在；結束碼 2）。加 `--json` 會列出檢查了哪些檔案、略過了哪些（與原因）、有多少舊程式碼沒檢查。

`verify` 是正式驗收：執行架構檢查與 `project.test-command`（有 `test-timeout` 上限），`--scope final` 再加上「`allow-legacy` 已清空」與「還在層外的模組」（後者只列出，不阻擋）。結果寫進 `.air/verify.json`，帶著程式碼（所有 `.py`、`AIR/config.toml`）、`.air/project.toml` 與 AIR 版本的指紋；任一項改變，紀錄就過期。測試指令沒設定、跑不起來或逾時，都不算通過。這份紀錄是本機的工作紀錄，有寫入權限的人可以改它；要可信的關卡，在 CI 重新執行 `verify`。

### 代碼

| 代碼 | 內容 | 套用範圍 | 設定（AIR/config.toml） |
|---|---|---|---|
| AIR000 | 檔案無法解析 | 所有層 | — |
| AIR001 | 禁用的內建函式（`open`、`print`、`eval` 等） | 純的層 | `banned-builtins` |
| AIR002 | 外部 import 不在白名單 | 純的層 | `imports.common`、`hints` |
| AIR003 | 層內循環 import | flows | `layers.flows.check-cycles` |
| AIR004 | 禁用的方法名稱（`.to_csv()`、`.write_text()` 等，不論物件型別） | 純的層 | `banned-methods` |
| AIR005 | 缺少必要參數（`sample` 的 `random_state`、`default_rng` 的 seed） | 純的層 | `required-args` |
| AIR006 | 禁用的函式（`pd.read_csv`、`np.random.rand`、`datetime.now` 等，會解析 import 別名） | 純的層 | `banned-calls` |
| AIR007 | 跨層方向錯誤 | 所有層 | `layers.*.internal`、`hints` |
| AIR008 | import 尚未遷移的舊模組 | 所有層 | `.air/project.toml` 的 `migration.allow-legacy` |
| AIR009 | AIR 套件或接點被修改：`AIR/` 的檔案與 `MANIFEST.sha256` 不符；跑過 install.sh 的電腦上，裝過的宿主的 hook 設定或指引區塊不見了 | 全專案檢查（結束前、commit 前、verify） | `AIR/MANIFEST.sha256` |
| AIR101 | 函式語句過多（僅提醒） | 所有層 | `soft.max-statements` |
| AIR102 | 函式過於複雜（僅提醒） | 所有層 | `soft.max-complexity` |

### 已知的檢查極限

- 方法名稱比對不看型別，所以會擋到同名但無害的方法（例如只回傳字串的 `df.to_json()`）。這是刻意的取捨。
- 沒有型別標註、直接當參數傳進 steps 的工具物件抓不到（STEP-2）。
- 其他函式庫自己的取時間、取亂數方法，沒列進 `banned-calls` 或 `required-args` 的話抓不到（STEP-3）。
- 函式長度、複雜度是用 AST 粗略計算，只用來提醒。
- pre-bash hook 會拆開 `bash -c "..."`、`sh -lc '...'`（最多三層）再檢查，但判斷不到腳本檔（`sh run.sh`）或變數展開裡的指令。

## 4. 設定檔

| 檔案 | 屬於 | 內容 | 誰可以改 |
|---|---|---|---|
| `AIR/config.toml` | 套件 | 所有規則的預設值 | 只在 AIR-dev 改 |
| `AIR/rules/*.md` | 套件 | 各層規則的來源 | 只在 AIR-dev 改 |
| `AIR/MANIFEST.sha256` | 套件 | 套件每個檔案的 SHA-256（`tests/` 除外），全專案檢查時比對 | 只在 AIR-dev 用 `python3 AIR/air.py manifest` 產生 |
| `.air/project.toml` | 專案 | 套件位置、測試指令與逾時、額外允許的模組、遷移階段、暫時允許的舊模組 | 使用者同意後才改 |
| `.air/history.jsonl` | 專案 | 每次階段轉移：時間、從哪到哪、commit、方式（normal／rollback／forced）、原因 | 由 `phase` 指令寫入 |
| `.air/python`、`.air/hosts` | 這台電腦 | Python 路徑、裝了哪些宿主的接點（不進版本控制） | 由安裝程式產生 |
| `.air/sessions/<session>.json` | 這台電腦 | 這個 session 已附過哪些層的規則（不進版本控制） | 由 hook 寫入 |
| `.air/verify.json` | 這台電腦 | 最近一次 `verify` 的結果與程式碼指紋（不進版本控制） | 由 `verify` 指令寫入 |

## 5. 遷移階段

`installed → analyzed → planned → layered → migrating → done`，記錄在 `.air/project.toml` 的 `migration.phase`。每個階段的做法見 `AIR/START.md`，進度記錄在 `docs/AIR-遷移報告.md`。

`python3 AIR/air.py phase <階段>` 一次只能前進一格，而且會檢查前置條件：

| 要進入 | 前置條件 |
|---|---|
| analyzed | `docs/AIR-遷移報告.md` 存在；`test-command` 已設定 |
| planned | 遷移報告存在 |
| layered | 各層目錄都存在；`check` 通過 |
| migrating | （只要目前是 layered） |
| done | 最近一次 `verify --scope final` 通過，而且之後程式碼與設定沒有變更 |

退回較早的階段用 `--rollback --reason <原因>`；特殊情況要略過前置條件用 `--force --reason <原因>`（只有使用者明確要求時才用）。每次轉移都會追加一行到 `.air/history.jsonl`。

## 6. 維護規範（在 AIR-dev 進行）

**在專案裡不要修改 `AIR/`**，更新時會被整包換掉（編輯工具會被 pre-edit hook 擋下；用其他方式改了，全專案檢查會回報 AIR009）。專案專屬的調整只能寫在 `.air/project.toml`。

新增一個宿主：在 `hosts.py` 加一個 `Host`（hook 設定檔、skills 目錄、根目錄的找法、支不支援 `ask`、要裝哪些 hook），`parse()` 補它的欄位別名，`tests/test_hosts.py` 加它的 payload fixture；安裝、移除、protect、AIR009、doctor 都會自動涵蓋。

在 AIR-dev 修改規則時：

1. **先決定規則放哪裡**（取第一個符合的）：
   - 只跟某一層有關 → `AIR/rules/<層>.md`
   - 只在做某種任務時需要 → 對應的 skill（`AIR/skills/`）
   - 每次工作都需要 → `AIR/AGENTS.md`（這一層最貴，應該極少新增）
2. **能用程式檢查的，也寫進 `AIR/config.toml`**；要新的檢查方式時，修改 `AIR/lib/airkit/checks.py`。
3. **數量上限**：`AGENTS.md` 常駐 3 條、每層最多 6 條、每個 skill 約 60 行（更長的內容拆到 skill 資料夾裡的檔案，並寫明「需要時才讀」）。超過時，先合併、刪除，或改成程式檢查。
4. **規則格式**：`- **<前綴>-<編號>【必須|建議】** <一句可以檢查的指令>。〔標記〕`。用「做什麼／不做什麼」，不寫「盡量」「適當」這類無法判斷的詞；一條規則只寫在一個地方；編號刪除後不重複使用；標記不能誇大。
5. **訊息格式**：`<規則編號>：<違反了什麼>。<怎麼修>（見 skill <名稱>）。`
6. **測試**：新增或修改的檢查，要在 `AIR/tests/` 加上「應該擋」與「應該放行」的案例各至少一個。測試只用標準庫，在 `AIR/` 目錄下執行 `python3 -m unittest discover -s tests -t .`（有 pytest 也可以直接用）。一次全部通過的測試，要故意把程式改壞，確認它真的會失敗。
7. **架構層級的決定**（新增層、換工具、推翻舊決定）：更新 `AIR/docs/設計說明.md` 的「主要設計決定」一節，只寫現行的決定。
8. 更新 `AIR/VERSION`。
9. 最後執行 `python3 AIR/air.py manifest` 更新 `MANIFEST.sha256`（`tests/test_integrity.py` 會確認它是最新的；忘了就會紅）。
