# AIR 規範說明

這份文件說明規則、檢查機制、設定檔與維護方法。給使用者與 AI 參考；AI 平常不需要讀它，只在需要查詢時才讀。

---

## 1. 分層

依賴方向由上往下；同一列的層互不依賴。各層都是套件（`.air/project.toml` 的 package-dir）底下的子套件。

```
main/                          組裝：載入 → 執行 flow → 儲存
flows/ │ adapters/ │ storage/  串接步驟 │ 包裝第三方工具 │ 所有讀寫
steps/                         純邏輯
contracts/                     跨層的型別（types.py）與介面（ports.py）
```

| 層 | 純的層 | 內部可以 import | 外部可以 import |
|---|---|---|---|
| contracts | 是 | contracts | 白名單 |
| steps | 是 | steps、`contracts.types` | 白名單 |
| flows | 是 | steps、flows、contracts | 白名單 |
| adapters | 否 | contracts | 任何套件 |
| storage | 否 | contracts | 任何套件 |
| main | 否 | 全部 | 任何套件 |

- **白名單**：標準庫的純計算模組（typing、dataclasses、collections、itertools、functools、math、statistics、decimal、re、json、datetime 等）、pandas、numpy，以及專案在 `.air/project.toml` 的 `imports.extra` 加入的模組。
- **純的層**另外還會檢查：I/O、`print`、讀時間、取亂數。
- **只有 flows 會呼叫 Protocol**：adapter 實作 `contracts/ports.py` 的 Protocol → main 建立 adapter 並注入 flow → flow 呼叫它，再把結果（資料）交給 steps。
- **舊程式碼**：套件內還沒搬進任何層的模組。不受檢查；但層不能 import 舊程式碼，遷移期間可以經使用者同意，在 `migration.allow-legacy` 暫時允許。

## 2. 規則從哪裡來、何時送到 AI 面前

| 時機 | 機制 | 內容 |
|---|---|---|
| 每次對話 | 專案的 `CLAUDE.md` 匯入 `AIR/AGENTS.md`；其他工具透過 `AGENTS.md` 的指引讀取 | 架構、前綴對照、3 條常駐規則 |
| 進入某一層 | Claude Code 在讀寫某目錄的檔案時，自動載入該目錄的 `CLAUDE.md` | 該層的規則（每層最多 6 條） |
| 做某種任務 | skill（`.claude/skills/air-*`） | 做法與判斷標準 |
| 違規當下 | 檢查訊息帶規則編號與修法 | 被違反的那條規則 |

規則前綴：`CTR`→contracts、`STEP`→steps、`FLOW`→flows、`ADP`→adapters、`IO`→storage、`MAIN`→main、`TEST`→tests。完整內容在 `AIR/rules/`，安裝時會複製到各層目錄成為 `CLAUDE.md`。

規則標記：〔hook 檢查〕所有違反方式都會被抓到；〔hook 部分檢查〕只抓得到部分寫法（規則中會舉出抓不到的例子）；沒有標記的完全靠自律。

## 3. 檢查

### 關卡

| 關卡 | 何時 | 範圍 | 違規時 |
|---|---|---|---|
| post-edit hook | Claude Code 每次編輯 `.py` 後 | 該檔案 | 回報（修改已寫入，必須修正） |
| pre-bash hook | Claude Code 每次執行 Bash 前 | 該指令 | 擋下略過 commit 前檢查的指令 |
| stop hook | Claude Code 要結束前 | 所有層 | 要求繼續修正（只提醒一次） |
| commit 前檢查 | 每次 `git commit` | 所有層 | commit 失敗 |

用 Bash 改檔不會觸發 post-edit，所以由 stop hook 補檢查。commit 前的檢查可以被人手動略過，目前沒有無法略過的關卡（需要 CI 加上分支保護）。

### 代碼

| 代碼 | 內容 | 套用範圍 | 設定（AIR/config.toml） |
|---|---|---|---|
| AIR000 | 檔案無法解析 | 所有層 | — |
| AIR001 | 禁用的內建函式（`open`、`print`、`eval` 等） | 純的層 | `banned-builtins` |
| AIR002 | 外部 import 不在白名單 | 純的層 | `imports.common`、`hints` |
| AIR003 | 層內循環 import | flows | `layers.flows.check-cycles` |
| AIR004 | 禁用的方法名稱（`.to_csv()`、`.write_text()` 等，不論物件型別） | 純的層 | `banned-methods` |
| AIR005 | 缺少必要參數（`sample` 的 `random_state`、`default_rng` 的 seed） | 純的層 | `required-args` |
| AIR006 | 禁用的函式（`pd.read_csv`、`np.random.rand`、`datetime.now` 等，會解析 import 別名） | 純的層 | `banned-calls` |
| AIR007 | 跨層方向錯誤 | 所有層 | `layers.*.internal`、`hints` |
| AIR008 | import 尚未遷移的舊模組 | 所有層 | `.air/project.toml` 的 `migration.allow-legacy` |
| AIR101 | 函式語句過多（僅提醒） | 所有層 | `soft.max-statements` |
| AIR102 | 函式過於複雜（僅提醒） | 所有層 | `soft.max-complexity` |

### 已知的檢查極限

- 方法名稱比對不看型別，所以會擋到同名但無害的方法（例如只回傳字串的 `df.to_json()`）。這是刻意的取捨。
- 沒有型別標註、直接當參數傳進 steps 的工具物件抓不到（STEP-2）。
- 其他函式庫自己的取時間、取亂數方法，沒列進 `banned-calls` 或 `required-args` 的話抓不到（STEP-3）。
- 函式長度、複雜度是用 AST 粗略計算，只用來提醒。
- pre-bash hook 判斷不到包在 `bash -c "..."` 或腳本裡的指令。

## 4. 設定檔

| 檔案 | 屬於 | 內容 | 誰可以改 |
|---|---|---|---|
| `AIR/config.toml` | 套件 | 所有規則的預設值 | 只在 AIR-dev 改 |
| `AIR/rules/*.md` | 套件 | 各層規則的來源 | 只在 AIR-dev 改 |
| `.air/project.toml` | 專案 | 套件位置、測試指令、額外允許的模組、遷移階段、暫時允許的舊模組 | 使用者同意後才改 |
| `.air/python` | 這台電腦 | Python 路徑（不進版本控制） | 由安裝程式產生 |

## 5. 遷移階段

`installed → analyzed → planned → layered → migrating → done`，記錄在 `.air/project.toml` 的 `migration.phase`。每個階段的做法見 `AIR/START.md`，進度記錄在 `docs/AIR-遷移報告.md`。

## 6. 維護規範（在 AIR-dev 進行）

**在專案裡不要修改 `AIR/`**，更新時會被整包換掉。專案專屬的調整只能寫在 `.air/project.toml`。

在 AIR-dev 修改規則時：

1. **先決定規則放哪裡**（取第一個符合的）：
   - 只跟某一層有關 → `AIR/rules/<層>.md`
   - 只在做某種任務時需要 → 對應的 skill（`AIR/skills/`）
   - 每次工作都需要 → `AIR/AGENTS.md`（這一層最貴，應該極少新增）
2. **能用程式檢查的，也寫進 `AIR/config.toml`**；要新的檢查方式時，修改 `AIR/lib/airkit/checks.py`。
3. **數量上限**：`AGENTS.md` 常駐 3 條、每層最多 6 條、每個 skill 約 60 行（更長的內容拆到 skill 資料夾裡的檔案，並寫明「需要時才讀」）。超過時，先合併、刪除，或改成程式檢查。
4. **規則格式**：`- **<前綴>-<編號>【必須|建議】** <一句可以檢查的指令>。〔標記〕`。用「做什麼／不做什麼」，不寫「盡量」「適當」這類無法判斷的詞；一條規則只寫在一個地方；編號刪除後不重複使用；標記不能誇大。
5. **訊息格式**：`<規則編號>：<違反了什麼>。<怎麼修>（見 skill <名稱>）。`
6. **測試**：新增或修改的檢查，要在 AIR-dev 的 `tests/` 加上「應該擋」與「應該放行」的案例各至少一個，執行 `.venv/bin/pytest`。
7. **架構層級的決定**（新增層、換工具、推翻舊決定）：更新 `AIR/docs/設計說明.md` 的「主要設計決定」一節，只寫現行的決定。
8. 更新 `AIR/VERSION`。
