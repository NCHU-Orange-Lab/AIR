# AIR 規範說明

這份文件說明規則、檢查機制、設定檔與維護方法。給使用者與 AI 參考；AI 平常不需要讀它，只在需要查詢時才讀。

---

## 1. 分層

依賴方向由上往下；同一列的層互不依賴。各層都是套件（`.air/project.toml` 的 package-dir）底下的子套件。

```
main/                          組裝：載入 → 執行 flow → 儲存
flows/ │ adapters/ │ storage/  串接步驟 │ 包裝第三方工具 │ 所有讀寫
steps/                         純邏輯
contracts/                     跨層的型別（types.py）與介面（ports.py）
```

| 層 | 純的層 | 內部可以 import | 外部可以 import |
|---|---|---|---|
| contracts | 是 | contracts | 白名單 |
| steps | 是 | steps、`contracts.types` | 白名單 |
| flows | 是 | steps、flows、contracts | 白名單 |
| adapters | 否 | adapters（不能循環）、contracts | 任何套件 |
| storage | 否 | storage（不能循環）、contracts | 任何套件 |
| main | 否 | 全部 | 任何套件 |

- **白名單**：標準庫的純計算模組（typing、dataclasses、collections、itertools、functools、math、statistics、decimal、re、json、datetime 等）、pandas、numpy，以及專案在 `.air/project.toml` 的 `imports.extra` 加入的模組。白名單也決定哪些第三方型別可以跨層當資料用（CTR-4、ADP-2）：預設只有 pandas、numpy。
- **adapters 的子套件**：一個第三方工具一個檔案，或一個子套件 `adapters/<工具>/` 依角色切檔（ADP-1：`data.py`、`model.py`、`loss.py`、`metrics.py`、`trainer.py`、`predictor.py`）。子套件底下的檔案都算 adapters 層：規則注入、檢查、審查都一樣。
- **純的層**另外還會檢查：I/O、`print`、讀時間、取亂數。
- **Protocol 由 flows 呼叫，steps 不能**：adapter 實作 `contracts/ports.py` 的 Protocol → main 建立 adapter 並注入 flow → flow 呼叫它，再把結果（資料）交給 steps。唯一的例外：adapter 要逐筆讀取放不進記憶體的資料時，接收 storage 實作、main 注入的 Protocol（見 skill `air-wrap-tool` 的 `examples/trainer.md`）。
- **舊程式碼**：套件內還沒搬進任何層的模組。不受檢查；但層不能 import 舊程式碼，遷移期間可以經使用者同意，在 `migration.allow-legacy` 暫時允許。
- **不歸 AIR 管的路徑**：`migration.exclude` 列的目錄或檔案（相對根目錄，可寫 `dir/**`；不是 glob）。不凍結、不進驗收指紋、不列進 survey 與層外模組清單，留在外面算正式的結局。層目錄底下的檔案不受影響，一律檢查。

## 2. 規則從哪裡來、何時送到 AI 面前

| 時機 | 機制 | 內容 |
|---|---|---|
| 每次對話 | 專案的 `AGENTS.md` 放著 `AIR/AGENTS.md` 的全文（1,500 字內）；`CLAUDE.md` 匯入它（使用者原有的 `CLAUDE.md` 則匯入 `AIR/AGENTS.md`） | 架構、前綴對照、3 條常駐規則 |
| session 開始、壓縮後 | hook：附上目前狀態（階段、違規數、現在該做的事），以及 `START.md` 當下階段的那一節；遷移暫停中改附「暫停中」與原因，不附那一節 | `status` 的內容、該階段的做法（不用再讀整份 START.md） |
| 進入某一層 | Claude Code：`.claude/rules/air-<層>.md`（`AIR/rules/<層>.md` 的複本，安裝時產生，`paths` 指向該層目錄），讀寫該層的檔案時由宿主自己載入，不經 hook；Codex：hook 在第一次修改該層的檔案時附上（同一個 session 只附一次；壓縮後重新附） | 該層的規則（每層最多 6 條） |
| 做某種任務 | skill（`.claude/skills/air-*`、`.agents/skills/air-*`） | 做法與判斷標準 |
| 違規當下 | 檢查訊息帶規則編號與修法 | 被違反的那條規則 |

規則前綴：`CTR`→contracts、`STEP`→steps、`FLOW`→flows、`ADP`→adapters、`IO`→storage、`MAIN`→main、`TEST`→tests。完整內容在 `AIR/rules/`。

**常駐內容的預算**：`python3 AIR/air.py doctor --context` 依宿主列出一開場就會載入的檔案與大小：Claude Code 的 `CLAUDE.md`（含 `@` 匯入，最多 4 層）、`.claude/rules/` 裡沒有 `paths` 的規則、使用者的 `~/.claude/CLAUDE.md` 與規則、自動記憶索引 `~/.claude/projects/<專案>/memory/MEMORY.md`（上限前 200 行或 25,000 bytes，尾端會被截掉）；Codex 的 `$CODEX_HOME` 與根目錄的 `AGENTS.md` 鏈（合計上限 `project_doc_max_bytes`，預設 32 KiB，到上限就停止加入，AIR 的區塊在尾端最先受影響）；以及 AIR 自己的 SessionStart 注入。有上限的項目到 80% 是注意，超過上限或 AIR 區塊落在上限外是問題；平常的 `doctor` 也會列出這些，`status` 只在有項目到 80% 以上時多一行。AIR 只讀這些檔案，不改、不擋。

規則標記：〔hook 檢查〕所有違反方式都會被抓到；〔hook 部分檢查〕只抓得到部分寫法（規則中會舉出抓不到的例子）；沒有標記的沒有程式檢查。沒有標記的規則、以及部分檢查抓不到的部分，由 skill `air-review` 在每批 commit 前做語意審查（見下面的 `review`）。

## 3. 檢查

### 關卡

| 關卡 | 何時 | 範圍 | 違規時 |
|---|---|---|---|
| pre-edit hook | 每次用編輯工具改檔前 | 該檔案的路徑 | 擋下受保護路徑（`AIR/`、hook 設定、`.git/`、AIR 複製的 skill）與分析／計畫階段對套件目錄、測試目錄裡 `.py` 的修改（`migration.exclude` 的路徑與套件外的腳本不擋；遷移暫停中不擋）；`.air/project.toml` 改成請使用者確認（Codex 沒有確認機制，改成提醒） |
| post-edit hook | 每次編輯 `.py` 後 | 該檔案 | 回報（修改已寫入，必須修正） |
| pre-bash hook | 每次執行 Bash 前 | 該指令（含 `bash -c`、`ssh host '…'` 裡的） | 擋下略過 commit 前檢查的指令 |
| stop hook | AI 要結束前 | 這個 session 動過的檔案（編輯工具記下的，加上 session 開始後內容變了的層內 `.py`）＋AIR009；`hooks.stop-scope = "all"` 時是所有層 | 要求繼續修正（只提醒一次） |
| commit 前檢查 | 每次 `git commit` | 所有層 | commit 失敗 |
| `verify` | 每批遷移結束、收尾時（由 AI 執行） | 所有層＋專案的測試指令（依既有失敗基準）＋黃金重播 | 驗收未通過；沒有通過的紀錄就不能進入 `done` |
| 語意審查（skill `air-review`） | 每批 commit 前（由 AI 執行） | 這次變更改到的層內 `.py`，對照沒有程式檢查的規則；審過沒變的檔案沿用 | priority 0、1 的發現要處理或向使用者說明，處理後只有改過的檔案要重審；不擋 commit，也不能推翻 `check`／`verify` |

用 Bash 改檔不會觸發 post-edit，所以 stop hook 拿 session 開始時各層檔案的快照（`.air/sessions/<session>.json`）比對，內容變了的就查；別的 session 在這之前留下的半成品不算，不會要這個 session 去修別人正在改的檔案。commit 前的檢查可以被人手動略過，目前沒有無法略過的關卡（需要 CI 加上分支保護）。

hook 自己壞掉（找不到 Python、payload 壞掉、程式例外）時放行、不擋工作，但會寫進 `.air/hook-errors.log`，`status` 與 `doctor` 顯示最近 24 小時的次數；commit 前檢查找不到 Python 則擋下 commit。hook 的輸出入一律 UTF-8、回應只用 ASCII，不受系統語系影響；給機器讀的路徑一律用 `/`。Python 由 `hooks/_python.sh` 找：`.air/python`、`python3.x`、`python3`、`python`、`py -3`，每個都真的執行版本檢查（Windows 的 `python3` 可能是 Microsoft Store 的假指令）。

### 宿主

規則、檢查與 skill 不分宿主；宿主的差異集中在 `AIR/lib/airkit/hosts.py`：hook 設定寫在哪、skill 裝在哪、怎麼找專案根目錄、payload 的欄位名稱、聽不聽得懂 `ask`。

| 宿主 | hook 設定 | skills | 差異 |
|---|---|---|---|
| Claude Code（Grok Build 讀同一份設定，`stopHookActive` 等欄位名稱的差異在 `hosts.parse()` 處理） | `.claude/settings.json` | `.claude/skills/` | 五個 hook（session 開始、編輯前、編輯後、執行 Bash 前、結束前）。各層規則用宿主內建的路徑規則：`.claude/rules/air-<層>.md`，讀寫該層時自己載入，不啟動 Python（2.6.1 以前是讀檔前的 hook，每次 Read 多一個 Python 行程）。Windows 上由 Git Bash 執行；沒有 Git Bash 時 Claude Code 改用 PowerShell，AIR 的 hook 無法執行（`doctor` 的冒煙測試會指出） |
| Codex | `.codex/hooks.json` | `.agents/skills/` | 五個 hook（同上）。沒有 Read 工具也沒有路徑規則，各層規則在第一次編輯該層時由 hook 附上；PreToolUse 不支援 `ask`，改成提醒；hook 要在 Codex 裡信任過才會執行；用 `git rev-parse --show-toplevel` 找根目錄 |

安裝時預設裝所有宿主（`--host` 可以只裝一種），`.air/hosts` 記錄這台電腦裝了哪些；AIR009 的接點檢查只要求裝過的宿主。`python3 AIR/air.py doctor` 列出每個宿主的接線狀態（hook 齊不齊、是不是舊格式、skill 是不是目前版本），並真的把每個 hook 跑一次（冒煙測試：結束碼要是 0 或 2、輸出要是合法的 UTF-8 JSON；宿主對其他失敗一律放行，只看設定抓不到），也確認 `.claude/rules/` 的每一份規則都在、是目前版本；只讀不修。

### `check`、`verify` 與 `review`

`check` 是快速診斷，結果分四種：**通過**、**違規**、**沒有檢查任何檔案**（各層目錄都不存在；結束碼 0，但不代表合規）、**輸入錯誤**（指定的檔案不存在；結束碼 2）。畫面上同一種違規（代碼與訊息相同）合併成一組，修法只印一次，底下列位置；結束前的檢查最多印 10 組，完整清單寫在 `.air/branches/<分支>/last-check.json`。加 `--json` 會逐條列出，並說明檢查了哪些檔案、略過了哪些（與原因）、有多少舊程式碼沒檢查。

`verify` 是正式驗收：執行架構檢查、`[tests]` 的 `command`（有 `timeout` 上限；舊鍵 `project.test-command` 仍可用；`--scope final` 有設 `[tests.final]` 就改跑它）與黃金重播，`--scope final` 再加上「`allow-legacy` 已清空」與「還在層外的模組」（後者只列出，不阻擋；`migration.exclude` 的路徑不列）。結果寫進 `.air/branches/<分支>/verify.json`（依分支分開，切分支不會互相覆蓋或誤判；detached 是 `detached-<sha12>`，不是 git repo 是 `no-git`），帶著程式碼的指紋（套件目錄與測試目錄的 `.py`、`verify.fingerprint-extra` 列的路徑、AIR 自己的程式與 `config.toml`；`migration.exclude` 的路徑不算）、`.air/project.toml` 與 AIR 版本；任一項改變，紀錄就過期。套件外會影響測試的檔案（conftest、設定檔）要自己列進 `fingerprint-extra`。測試指令沒設定、跑不起來或逾時，都不算通過。

測試結果的判斷：`[tests]` 沒設 `results` 時只認結束碼 0。設了（指令寫出的 JUnit XML，`pytest --junit-xml`；跑之前會先刪掉舊檔）就依**既有失敗基準**：`verify --record-baseline` 把目前失敗的測試記進 `.air/test-baseline.json`（進版本控制，每個套件一份），之後「失敗減基準」為空就通過（結束碼 1 也算），並列出新增的失敗與基準裡已修好的；結束碼不是 0 或 1（用法錯誤、中斷、沒收集到測試）算錯誤。研究型專案本來就有環境性失敗，只認 0 永遠拿不到驗收。

黃金重播：`[[tests.golden]]` 寫固定輸入的指令與輸出檔，`golden record` 跑一次把每個輸出的 sha256 記進 `.air/golden.json`（進版本控制，只存雜湊）；`verify` 依 `scope` 重跑比對，變了或缺了就不通過（輸出留在原處可以 diff），還沒記錄算錯誤。逐位元比對，輸出必須是確定的；重錄只由使用者決定（TEST-5）。這份紀錄是本機的工作紀錄，有寫入權限的人可以改它；要可信的關卡，在 CI 重新執行 `verify`。

`review` 是語意審查的程式部分，判斷本身由 AI 照 skill `air-review` 做。`python3 AIR/air.py review` 用 git 界定這次的變更（相對 HEAD、含未 commit 的修改；`--base <分支>` 則相對 merge-base），依層列出要對照的規則（沒有〔hook 檢查〕標記的；部分檢查的只審抓不到的部分）與出處，每層只列一次，底下是該層改到的 `.py` 與改到的行。上次審過、內容沒變（sha256 相同）的檔案只列名字並沿用上次的發現，不必重審。AI 審完用 `--result` 交回固定格式的 JSON，程式驗證後才記進 `.air/branches/<分支>/review.json`：規則要存在、要是該層的、不能是 `check` 負責的；行號要落在改到的行附近（既有問題不報）；信心不到 0.5 的不收；`overall` 要與發現一致（含沿用的發現）。無效的結果不記錄（結束碼 2）；有 priority 0、1 的發現結束碼 1。紀錄每個檔案一筆、綁定該檔的內容，之後哪個檔案又改了，只有那個檔案要重審（`status` 會顯示幾個）。`--bundle` 把每個待審檔案的差異（新檔案整個列出加行號）接在範圍後面，一次拿齊；審查預設自己做，交給子 agent 時把這段輸出整段貼給它，它就不用重跑。

### 已知的檢查極限

- 方法名稱比對不看型別，所以會擋到同名但無害的方法（例如只回傳字串的 `df.to_json()`）。這是刻意的取捨。
- 沒有型別標註、直接當參數傳進 steps 的工具物件抓不到（STEP-2）。
- 其他函式庫自己的取時間、取亂數方法，沒列進 `banned-calls` 或 `required-args` 的話抓不到（STEP-3）。
- 函式長度、複雜度是用 AST 粗略計算，只用來提醒。
- pre-bash hook 會拆開 `bash -c "..."`、`sh -lc '...'`、`ssh host '...'`（最多三層）再檢查，但判斷不到腳本檔（`sh run.sh`）或變數展開裡的指令；遠端 clone 自己發出的 commit 不經過 AIR，以 CI 為準。
- hook 自己壞掉時宿主一律放行（結束碼 0、2 以外都算非阻擋錯誤）；AIR 只能留下紀錄、在 `doctor` 冒煙測試時抓到，擋不住。

## 4. 設定檔

| 檔案 | 屬於 | 內容 | 誰可以改 |
|---|---|---|---|
| `AIR/config.toml` | 套件 | 所有規則的預設值 | 只在 AIR-dev 改 |
| `AIR/rules/*.md` | 套件 | 各層規則的來源 | 只在 AIR-dev 改 |
| `AIR/MANIFEST.sha256` | 套件 | 套件每個檔案的 SHA-256（`tests/` 與 `.github/` 除外），全專案檢查時比對 | 只在 AIR-dev 用 `python3 AIR/air.py manifest` 產生 |
| `.claude/rules/air-<層>.md` | 專案（接點） | `AIR/rules/<層>.md` 的複本，前面加 `paths` 指向該層目錄；Claude Code 讀寫該層時自己載入。不見了算 AIR009 | 由安裝程式產生，更新 AIR 後重跑 `install.sh` 會換成新版 |
| `.air/project.toml` | 專案 | 套件位置、測試指令與逾時、測試結果檔與基準（`[tests]`）、收尾套件（`[tests.final]`）、黃金重播（`[[tests.golden]]`）、額外允許的模組、遷移階段、暫時允許的舊模組、不歸 AIR 管的路徑（`migration.exclude`）、指紋額外路徑（`verify.fingerprint-extra`）、結束前檢查的範圍（`hooks.stop-scope`） | 使用者同意後才改 |
| `.air/history.jsonl` | 專案 | 每次階段轉移、暫停與繼續：時間、從哪到哪、commit、方式（normal／rollback／forced／pause／resume）、原因 | 由 `phase`、`pause`、`resume` 指令寫入 |
| `.air/paused.json` | 專案 | 遷移暫停中：時間、暫停時的階段、原因（`resume` 時移除） | 由 `pause`／`resume` 指令寫入 |
| `.air/test-baseline.json` | 專案 | 既有失敗基準：每個套件本來就失敗的測試清單、時間、commit | 由 `verify --record-baseline` 寫入 |
| `.air/golden.json` | 專案 | 黃金重播的輸出雜湊（每筆：指令、每個輸出檔的 sha256、時間、commit） | 由 `golden record` 寫入（只由使用者決定） |
| `.air/python`、`.air/hosts` | 這台電腦 | Python 路徑、裝了哪些宿主的接點（不進版本控制） | 由安裝程式產生 |
| `.air/sessions/<session>.json` | 這台電腦 | 這個 session 已附過哪些層的規則（Codex）、編輯工具動過的檔案、開始時各層 `.py` 的快照（不進版本控制） | 由 hook 寫入 |
| `.air/hook-errors.log` | 這台電腦 | hook 自己壞掉的紀錄：UTC 時間、哪個 hook、原因（不進版本控制，可以刪） | 由 hook 寫入 |
| `.air/metrics.jsonl` | 這台電腦 | 成本的代理指標：verify、審查範圍（字數）、審查交回、post-edit 與 Stop 擋下、survey（不進版本控制，可以刪） | 由各指令與 hook 追加 |
| `.air/branches/<分支>/verify.json` | 這台電腦 | 這個分支最近一次 `verify` 的結果與程式碼指紋（不進版本控制） | 由 `verify` 指令寫入 |
| `.air/branches/<分支>/review.json` | 這台電腦 | 這個分支最近一次語意審查的結果，每個檔案一筆（不進版本控制） | 由 `review --result` 寫入 |
| `.air/branches/<分支>/last-check.json` | 這台電腦 | 結束前的檢查有違規時的完整清單（不進版本控制） | 由 stop hook 寫入 |

## 5. 遷移階段

`installed → analyzed → planned → layered → migrating → done`，記錄在 `.air/project.toml` 的 `migration.phase`。每個階段的做法見 `AIR/START.md`，進度記錄在 `docs/AIR-遷移報告.md`。

`python3 AIR/air.py phase <階段>` 一次只能前進一格，而且會檢查前置條件：

| 要進入 | 前置條件 |
|---|---|
| analyzed | `docs/AIR-遷移報告.md` 存在；測試指令（`[tests]` 的 `command`）已設定 |
| planned | 遷移報告存在 |
| layered | 各層目錄都存在；`check` 通過 |
| migrating | （只要目前是 layered） |
| done | 最近一次 `verify --scope final` 通過，而且之後程式碼與設定沒有變更 |

退回較早的階段用 `--rollback --reason <原因>`；特殊情況要略過前置條件用 `--force --reason <原因>`（只有使用者明確要求時才用）。每次轉移都會追加一行到 `.air/history.jsonl`。寫入 `.air/project.toml` 前會比對檔案裡的階段跟這次讀到的一樣，不一樣就拒絕（兩個 session 同時推進不會互相覆蓋）；寫暫存檔再替換，中斷不留半份。

遷移要擱置時，由使用者執行 `python3 AIR/air.py pause --reason <原因>`（要寫原因）：階段保留，分析／計畫階段的 `.py` 凍結解除，session 開始改附「暫停中」與原因而不是該階段的做法，`phase` 在暫停中會被拒絕；架構檢查、commit 前檢查照常，新程式仍要寫進對應的層。`python3 AIR/air.py resume` 繼續。暫停與繼續都記進 `.air/history.jsonl`。AI 不應自己執行這兩個指令（START.md 與 AGENTS.md 寫明）。

## 6. 維護規範（在 AIR-dev 進行）

**在專案裡不要修改 `AIR/`**，更新時會被整包換掉（編輯工具會被 pre-edit hook 擋下；用其他方式改了，全專案檢查會回報 AIR009）。專案專屬的調整只能寫在 `.air/project.toml`。

新增一個宿主：在 `hosts.py` 加一個 `Host`（hook 設定檔、skills 目錄、根目錄的找法、支不支援 `ask`、要裝哪些 hook、有沒有內建的路徑規則目錄 `rules_dir`），`parse()` 補它的欄位別名，`tests/test_hosts.py` 加它的 payload fixture；安裝、移除、protect、AIR009、doctor 都會自動涵蓋。有 `rules_dir` 的宿主各層規則由它自己載入，hook 不再注入。

在 AIR-dev 修改規則時：

1. **先決定規則放哪裡**（取第一個符合的）：
   - 只跟某一層有關 → `AIR/rules/<層>.md`
   - 只在做某種任務時需要 → 對應的 skill（`AIR/skills/`）
   - 每次工作都需要 → `AIR/AGENTS.md`（這一層最貴，應該極少新增）
2. **能用程式檢查的，也寫進 `AIR/config.toml`**；要新的檢查方式時，修改 `AIR/lib/airkit/checks.py`。沒有程式檢查的規則（沒有標記、或標為部分檢查）會自動進入語意審查的範圍，不用另外登記。
3. **數量上限**：`AGENTS.md` 常駐 3 條、全文不超過 1,500 字；每層最多 6 條、每條規則本文不超過 200 字；每個 skill 約 60 行（更長的內容拆到 skill 資料夾裡的檔案，並寫明「需要時才讀」）。超過時，先合併、刪除，或改成程式檢查；字數由 `tests/test_rules.py` 核對，不要放寬上限。
4. **規則格式**：`- **<前綴>-<編號>【必須|建議】** <一句可以檢查的指令>。〔標記〕`。用「做什麼／不做什麼」，不寫「盡量」「適當」這類無法判斷的詞；一條規則只寫在一個地方；編號刪除後不重複使用；標記不能誇大。`AIR/lib/airkit/rules.py` 會解析這個格式（`tests/test_rules.py` 確認每層的數量、編號與標記），寫錯格式的規則不會被 `review` 列出。
5. **訊息格式**：`<規則編號>：<違反了什麼>。<怎麼修>（見 skill <名稱>）。`
6. **測試**：新增或修改的檢查，要在 `AIR/tests/` 加上「應該擋」與「應該放行」的案例各至少一個。測試只用標準庫，在 `AIR/` 目錄下執行 `python3 -m unittest discover -s tests -t .`（有 pytest 也可以直接用）。一次全部通過的測試，要故意把程式改壞，確認它真的會失敗。push 到 `main` 與 pull request 時，GitHub Actions（`.github/workflows/test.yml`）會用 Python 3.11、3.12、3.13、3.14 在 ubuntu 與 Windows 跑同一個指令，另外把標準輸出入強制成 cp950 再跑一遍，全部都要綠。
7. **架構層級的決定**（新增層、換工具、推翻舊決定）：更新 `AIR/docs/設計說明.md` 的「主要設計決定」一節，只寫現行的決定。
8. 更新 `AIR/VERSION`。
9. 最後執行 `python3 AIR/air.py manifest` 更新 `MANIFEST.sha256`（`tests/test_integrity.py` 會確認它是最新的；忘了就會紅）。
