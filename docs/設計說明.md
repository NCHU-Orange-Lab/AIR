# AIR 設計說明

> 給維護這套規範的人：說明為什麼這樣設計、目前有哪些設計決定與限制，以及設計過程中學到的事。
> 設計決定只列出現行的版本；之後有變更時，直接改寫第 4 節。

---

## 1. 目的

1. **流程與步驟分開**：步驟是純函式，流程只負責串接，I/O 交給最外層（函式式核心、命令式外殼）。
2. **讓 AI 遵守得了**：不一次給 AI 全部規則，只給跟它當下工作有關的少量規則。
3. **能檢查的就用程式強制**，不能檢查的才靠文字和 AI 的判斷。
4. **能接入第三方工具**（例如 YOLO），又不破壞分層。
5. **能重複用在很多專案**：把資料夾放進既有專案，AI 就能照著把專案重構成這個架構。

---

## 2. 設計原則

1. **規則依時機分批送給 AI**：常駐、依位置、依任務、違規當下。
2. **能機械判斷的交給程式，需要判斷力的交給 AI**：程式負責檢查，skills 負責教做法和判斷標準。
3. **規則只有一個來源**：規則文字在 `AIR/rules/`，程式檢查的設定在 `AIR/config.toml`；腳本只負責執行，不另外記規則。
4. **軟規則只提醒，不擋**：函式長度、複雜度在任何關卡都不會造成失敗，避免 AI 為了過關而過度拆分。
5. **預設禁止**：純的層採用 import 白名單，不用黑名單。
6. **標記要誠實**：只能檢查到一部分的規則，要標〔hook 部分檢查〕並舉出抓不到的例子。
7. **規則數量有上限**：常駐 3 條（全文 1,500 字內）、每層最多 6 條（每條 200 字內）、每個 skill 約 60 行。
8. **檢查工具本身也要有測試**：測試跟著套件走（`AIR/tests/`），只用標準庫，任何環境都能跑。
9. **能用平台的內建機制，就不要自己做**。
10. **套件不能污染專案**：不覆蓋不是自己建立的東西；可以重複安裝；移除後還原原本的檔案；不留下快取或機器專屬的檔案。
11. **重構既有專案要分階段、可以喊停**：每個階段都停下來等使用者核准，一批一個 commit。

---

## 3. 運作方式

### 套件與專案的分界

```
AIR/              套件：更新時整包換掉，專案裡不修改
.air/             專案設定：更新時保留
接點              CLAUDE.md、AGENTS.md、.claude/、.codex/、.agents/、commit 前檢查
                  —— 全部由 install.sh 建立、uninstall.sh 移除
```

### 規則如何送到 AI 面前

| 時機 | 機制 |
|---|---|
| 每次對話 | 專案的 `AGENTS.md` 放著 `AIR/AGENTS.md` 的全文（1,500 字內）；`CLAUDE.md` 匯入它 |
| session 開始、壓縮後 | SessionStart hook 附上目前狀態（由磁碟重新算，不信任對話裡的摘要），以及 START.md 當下階段的那一節（整份近 4,000 字，5/6 跟當下無關）；遷移暫停中改附「暫停中」與原因，不附那一節 |
| 進入某一層 | PreToolUse hook：第一次讀或改某一層的檔案時，用 additionalContext 附上 `AIR/rules/<層>.md`，同一個 session 只附一次；壓縮後重新附 |
| 做某種任務 | skills（`.claude/skills/air-*`、`.agents/skills/air-*`） |
| 違規當下 | 檢查訊息帶規則編號與修法 |
| 每批 commit 前 | skill `air-review`：`air.py review` 用 git 界定這次的變更，依層列出要對照的規則（每層一次）與改到的檔案；審過沒變的檔案沿用；`--bundle` 連差異一起印，交給子 agent 時整段貼給它。AI 審完交回固定格式的結果，程式驗證後每個檔案記一筆 |

### 檢查

單一指令 `air.py check` 負責所有規則（AIR000–AIR008、AIR101–AIR102），由四道關卡呼叫：編輯後、執行 Bash 前（擋下略過檢查的指令）、結束前、commit 前。只檢查層內的程式；舊程式碼不檢查，所以遷移到一半時專案仍可以正常 commit。

36 條規則裡只有 10 條有程式檢查（7 條完整、3 條部分），其餘由語意審查補上：程式做能機械判斷的部分（範圍、規則出處、結果的驗證與紀錄），判斷由 AI 做；審查結果只是參考，不擋 commit，也不能推翻 `check`／`verify`。

## 4. 主要設計決定

| 決定 | 理由 |
|---|---|
| 做成可以放進專案根目錄的資料夾，大部分內容留在 `AIR/` 裡 | 更新時整包替換即可；專案根目錄只增加少量、可以完整移除的接點 |
| 不使用 copier 等範本工具 | 整包替換加上可重複執行的 install.sh，就能做到更新；少一個依賴 |
| 套件裡不能有 `.git`；開發 repo（AIR-dev）與套件（`AIR-dev/AIR/`）分開 | 內嵌的 `.git` 會讓專案的 git 不追蹤套件內容 |
| 啟動方式是對 AI 說「照 AIR/START.md 安裝」 | Claude Code 不會自動讀取子資料夾的規則，至少需要一個啟動動作；用一句話啟動，任何 AI 工具都能用 |
| 專案設定放在 `.air/`，不放在 `AIR/` 裡 | 更新時整包替換套件，專案設定才不會遺失 |
| `.air/python` 不進版本控制 | 路徑因機器而異；每個 clone 都要執行一次 install.sh（git hook 本來就需要） |
| 零依賴：只需要 Python 3.11+ | 不干擾專案原本的工具與環境（poetry、uv、conda、沒有 pre-commit 的專案） |
| 所有檢查收進自寫的 `air.py`，取代 ruff、import-linter | 零依賴；分層方向從「結束前才檢查」變成「每次編輯就檢查」；一套設定、一套測試 |
| 用名稱比對與別名解析，不做型別推論 | `to_csv`、`sample` 這類規則不需要知道型別；代價是會擋到同名但無害的方法 |
| 「舊程式碼區」取代違規基準線 | 只檢查層內的程式，舊程式碼照常運作；層對舊模組的依賴要明確列在 allow-legacy，並寫上原因 |
| 遷移分 6 個階段，每個階段停下來等核准 | 分類需要判斷力，重構有風險；每批先補行為保護測試，一批一個 commit，隨時可以回退 |
| 階段轉移一次一格、有前置條件、每次記錄（`.air/history.jsonl`） | `phase` 原本只是改一個字串，AI 可以從 installed 直接設成 done；「做完要核准」不能只靠文字 |
| `check` 與 `verify` 分開：`check` 是每次編輯的快速診斷，`verify` 才執行測試指令並寫下綁定程式碼指紋的驗收紀錄 | 「沒有違規」不等於「有驗收」；每次編輯都跑完整測試太慢。進入 `done` 需要一份新鮮的 final 驗收紀錄 |
| `check` 區分「通過」與「沒有檢查任何檔案」 | 各層都不存在時原本也回「通過」，空範圍會被當成合規的證據 |
| 「不要修改 `AIR/`」「分析／計畫階段不改程式」「改 `.air/project.toml` 要同意」用 PreToolUse hook 擋（受保護路徑）；`MANIFEST.sha256` 在結束前與 commit 前兜底 | 需要 AI「記得」的事都不可靠（學到的事第 4 條）；hook 攔不到 Bash 寫檔，所以要有事後的完整性檢查（AIR009） |
| 「什麼算使用者同意」寫進 START.md，同意的原話記進遷移報告 | 「沒有反對」「自己寫的計畫」都曾被當成授權；留下原話，事後才對得起來 |
| 遷移期間在舊模組保留轉接，收尾時再移除 | 呼叫端不用一次全改，每一批都能保持專案可以執行 |
| 分成六層，最底層是 contracts | Protocol 如果放在 steps，steps 就擁有一個自己不准用的東西，外層也被迫依賴 steps |
| Protocol 由 flows 呼叫，steps 不能；adapter 只在逐筆讀取放不進記憶體的資料時，接收 storage 實作、main 注入的 Protocol | steps 才能維持純函式，而且可以檢查。adapter 的例外不改依賴方向（adapters 仍只 import contracts 與同層），讀檔仍留在 storage |
| flows 可以呼叫子流程，但不能循環 | 大流程由小流程組成很常見 |
| adapters、storage 可以 import 同層的模組，但不能循環（AIR003，訊息指回 ADP-6、IO-4） | 原本只許 contracts：一個工具拆成模型、資料、訓練迴圈就得塞在同一個檔。業界的深度學習模板與框架（lightning-hydra-template、victoresque/pytorch-template、ultralytics、detectron2、mmdetection）一律依角色切檔、同套件互相 import。六層裡其他四層本來就允許同層，這是補齊一致性；開放的同時用循環檢查當護欄，跟 flows 一樣 |
| ADP-1：一個工具一個檔案，或一個子套件 `adapters/<工具>/` 依角色切檔（`data`、`model`、`loss`、`metrics`、`trainer`、`predictor`） | 檔名照業界公認的角色（data_loader／model／loss／metric／trainer），人和 AI 都認得；工具自帶完整流程（YOLO）時仍是一個檔。子套件底下的檔案都算 adapters 層，注入、檢查、審查不用特別處理 |
| 跨層的資料型別只認白名單內的資料函式庫：CTR-4、ADP-2 與 `imports.extra` 對齊；框架的張量要跨層，由專案經使用者同意加進白名單 | 業界的 structures（detectron2、mmdet）直接帶 tensor；AIR 預設只認 numpy、pandas，steps 與 flows 的測試才不需要框架。要不要付 tensor→numpy 的轉換代價，是專案的決定，套件只提供開關並要求同意 |
| IO-5：資料目錄依階段分（raw、interim、processed）、輸出目錄在套件外、都不進版本控制 | 直接借 cookiecutter-data-science 與 Kedro 的慣例，不自己發明；路徑仍然只從設定檔來（IO-1） |
| 不設 utils 層 | 業界每個模板都有 `utils/`，但它是「不知道放哪」的集合，分層檢查對它無能為力；純計算進 steps，其餘各歸其位 |
| main 的入口依任務命名（train、evaluate、predict） | 業界模板的入口都是 train.py、eval.py、predict.py；MAIN-4 一條流程一個函式，名稱跟著任務走 |
| storage 的規則前綴維持 `IO` | 規則編號一旦用過就不改 |
| 套件產生的檔案都加上標記（`AIR:MANAGED`、`.air-managed`、標記區塊） | 安裝與移除只動自己的東西 |
| 宿主的差異集中在 `hosts.py`（hook 設定檔、skill 位置、根目錄的找法、聽不聽得懂 `ask`、payload 的欄位名稱）；checks、protect、verify 都不知道宿主是誰 | 三份 harness 分析的共同結論：宿主協定塞進 checker，每多一個宿主就要改一次核心。hook 腳本把宿主名稱當參數傳進來，不用猜 |
| 各層規則改由 hook 在第一次讀寫該層時注入（additionalContext），不再放各層目錄的 `CLAUDE.md` | 只有 Claude Code 會自動載入子目錄的 CLAUDE.md，Codex 不會；hook 在兩邊都觸發，而且可以在測試裡驗證。注入紀錄依 session 記在 `.air/sessions/`，SessionStart（含壓縮）清掉 |
| `AGENTS.md` 放常駐規則全文，不只放「先讀 AIR/AGENTS.md」 | Codex 只串接 AGENTS.md 本文、不處理 `@` 匯入；「先讀」靠自律。規則仍只有 `AIR/AGENTS.md` 一個來源，安裝時複製 |
| AIR 建立的 `CLAUDE.md` 匯入 `AGENTS.md`；使用者原有的 `CLAUDE.md` 匯入 `AIR/AGENTS.md` | 前者讓 Claude Code 也讀到使用者 AGENTS.md 的內容；後者因為有了 CLAUDE.md 之後 Claude Code 不讀 AGENTS.md，不會讀到兩份 |
| Codex 的 PreToolUse 不支援 `ask`：改成 additionalContext 提醒 | 送 `ask` 會被判為無效輸出，hook 失敗後 fail-open，什麼都沒攔到；提醒至少把「要同意」送到模型面前 |
| 預設裝所有支援的宿主，`.air/hosts` 記錄這台電腦裝了哪些 | 同一個專案可能有人用 Claude Code、有人用 Codex；接點進版本控制，誰 clone 都能用。AIR009 的接點檢查只要求裝過的宿主，否則只裝一種的人會一直被報錯 |
| `doctor` 只讀、不修 | 修法都是「重跑 install.sh」；診斷與修復分開，才不會把「看起來正常」寫成正常 |
| 語意審查做成 skill＋程式（`review`）：程式界定範圍、列出規則與出處、驗證並記錄結果；判斷由 AI 做 | 26 條規則沒有程式檢查，原本完全靠自律。範圍、出處、行號由程式給，AI 不用數行號也不能捏造引用；結果要通過驗證（規則存在、是該層的、不是 `check` 負責的、行號落在變更內、信心與優先級、結論一致）才算數，無效的結果不是通過 |
| 語意審查只在批次邊界做、不擋 commit、不能推翻 `check`／`verify` | 模型審查會有誤判；每個動作都審成本太高，不穩定的判斷不該成為硬關卡。先有一個受限的審查，量測後再決定要不要擋 |
| 審查只收這次變更引入的問題：行號要落在改到的行附近，信心不到 0.5 不收 | 既有問題混進來會淹沒這批真正的問題；「不確定就不報」要有機械的門檻，不然只是一句話 |
| 規則檔是規則的單一來源：`rules.py` 解析 `AIR/rules/*.md` 的格式與標記，決定哪些規則進入審查 | 新增一條沒有程式檢查的規則，不用另外登記就會被審；標記寫錯（誇大成〔hook 檢查〕）會讓那條規則從審查消失，所以測試會核對標記 |
| 用 shlex 解析指令，判斷是否在略過 commit 前的檢查 | 正規表示式會誤判 commit 訊息裡的文字 |
| 輸出入一律 UTF-8（`air.py` 開頭 reconfigure，hook 腳本加 `-X utf8`），hook 的回應只用 ASCII | 實戰平台是 zh-TW Windows（cp950）：規則注入變亂碼，含中文 commit 訊息的 payload 解析失敗而放行，guard 時有時無。不能靠使用者設環境變數（`python -I` 會忽略 `PYTHONIOENCODING`），要在自己的程式裡固定 |
| Python 由 `hooks/_python.sh` 找：`.air/python`、`python3.x`、`python3`、`python`、`py -3`，每個都真的執行版本檢查 | Windows 的 `python3` 常是 Microsoft Store 的假指令；新的 git worktree 沒有 `.air/python`，hook 原本退回 `python3` 就 exit 49、整個靜默失效 |
| hook 自己壞掉時 fail-open，但寫 `.air/hook-errors.log`，`status` 與 `doctor` 顯示；commit 前檢查找不到 Python 則擋下 | 宿主對 0、2 以外的結束碼一律放行、stderr 也不給模型看；靜默放行等於強制機制消失，正是學到的事第 4 條說不可靠的那種規則。commit 是關卡，不能放行 |
| `doctor` 真的把每個 hook 跑一次（冒煙測試） | 只檢查設定在不在，抓不到「跑不起來」 |
| 給機器讀的路徑一律 POSIX（`/`），交回的審查結果先正規化 | Windows 上審查者交回 `git diff` 看到的 `demo/flows/report.py`，卻被反斜線的範圍清單拒絕，一再重交 |
| `status` 附本機時間 | AI 手寫的日期曾比機器時鐘超前 1–2 天；寫日期要有依據 |
| 審查紀錄每個檔案一筆、綁定內容的 sha256；內容沒變的檔案沿用，只有改過的重審 | 原本整批一個指紋：修掉一個發現整批作廢，一批 12 個模組要再讀 6,028 行。這是實戰中最大的 token 放大器之一。代價是看不到間接影響（A 改了讓 B 不合規而 B 沒變），靠全專案的程式檢查補 |
| `review` 的規則每層只列一次 | 實測一批的範圍輸出有 61% 是逐檔重印的規則文字 |
| `check` 與 Stop 同一種違規只印一次修法；Stop 最多 10 組，完整清單寫 `.air/last-check.json` | 實測 29 個違規有 49% 是重複的修法文字；Stop 印 40 條再逼 AI 多做一輪，只是在燒 token |
| `survey --out`：完整表寫檔，畫面只印摘要 | 每個模組約 166 字，幾百個模組一次印進對話就是幾萬 token，而且之後每一輪都帶著 |
| SessionStart 附上 START.md 當下階段的那一節 | START.md 要求「只讀那個階段」，但讀檔工具一次讀整份 |
| 成本的代理指標寫 `.air/metrics.jsonl`，`status` 顯示累計 | AIR 看不到真實的 token；省 token 的改動要能用數字證明，不能只靠估算 |
| 遷移可以暫停（`pause --reason`／`resume`）：階段保留、記進 history；暫停中解除分析／計畫階段的 `.py` 凍結、session 開始改附「暫停中」與原因、`phase` 被拒絕；架構檢查照常 | 實戰中遷移停在分析階段好幾週，整個 repo 的 `.py` 都被凍結，使用者只能把 AIR 拆掉。「暫停」是正式的出口：留下原因與紀錄，比拆掉或硬推階段都好；只由使用者執行，AI 看到暫停就照一般開發 |
| 語意審查預設自己審；只有使用者要求或待審檔案十個以上才交子 agent，而且用 `review --bundle` 把範圍與差異整段貼給它 | 子 agent 從零開始：要重跑 review、git diff、讀檔，同樣的內容再讀一遍；自審的偏誤沒有量測到，token 翻倍量得到 |
| `AGENTS.md` 全文 1,500 字內（砍掉 skills 與 hooks 一節、指令縮成三行、架構圖改成一句話），每條規則 200 字內；由測試核對 | `AGENTS.md` 每一輪都在，2,439 字裡有五分之一在介紹 skill 與 hook：skill 由宿主依描述觸發、hook 的行為在違規當下才需要知道，都不必常駐。上限寫成測試，不然會再長回去（學到的事 1） |
| 專案定位是通用資料處理，文件使用繁體中文 | YOLO 與 PyTorch 只當作第三方工具的範例（`skills/air-wrap-tool/examples/`） |

## 5. 已知限制

| 限制 | 目前的處理 |
|---|---|
| 只支援 Python 專案 | START.md 的前置檢查會停下來告知 |
| 沒有無法略過的關卡（AIR 的檢查都在本機） | commit 前檢查可以被人手動略過；要擋得住，專案要在自己的 CI 重跑 `verify` 並開分支保護。AIR 自己的 repo 已用 GitHub Actions（`.github/workflows/test.yml`）在 push 到 `main` 與 pull request 時以 Python 3.11 到 3.14 在 ubuntu 與 Windows 跑同一個測試指令，另外以 cp950 跑一遍；`main` 的分支保護要求 ubuntu 的四個版本通過才能合併 |
| hook 自己壞掉時擋不住，只能記錄 | 宿主對 0、2 以外的結束碼一律放行。Claude Code 2.1.295 起可以對單一 hook 設 `onFailure: "block"`，要不要對保護型 hook（編輯前、Bash 前）開，列在待決事項 |
| 驗收紀錄（`.air/verify.json`）是本機的工作紀錄，有寫入權限的人或 AI 可以改它；`--force` 會留下紀錄但擋不住 | 要可信的關卡，在 CI 重新執行 `verify`；`history.jsonl` 讓事後看得出有沒有強制跳過 |
| pre-edit hook 只攔宿主的編輯工具；用 Bash 寫 `AIR/` 或改 hook 設定，要到結束前或 commit 前的全專案檢查才抓到（AIR009） | 這段時間裡的檢查結果可能是被改過的 checker 算的；可信的結果仍要由 CI 用受控版本的 AIR 重算 |
| 每個 clone 都要執行一次 install.sh | 寫在 README；git hook 不進版本控制。沒有 `.air/python` 時 hook 會自己找 Python，所以新的 worktree 裡 hook 仍然有效，只有 commit 前檢查要重新安裝 |
| pre-bash hook 判斷不到腳本檔（`sh run.sh`）或變數展開裡的指令（`bash -c "..."` 會拆開，最多三層） | 盡力而為；權威的關卡是 commit 前檢查 |
| 沒有型別標註、直接傳進 steps 的工具物件抓不到 | STEP-2 標為〔部分〕 |
| 其他函式庫自己的取時間、取亂數方法 | STEP-3 標為〔部分〕；需要時加進 `banned-calls` 或 `required-args` |
| 方法名稱比對會擋到同名但無害的方法 | 刻意的取捨 |
| 函式長度、複雜度是粗略計算 | 只用於提醒 |
| `.pre-commit-config.yaml` 的 `repos:` 不是最後一個頂層設定時，無法自動加入 | 安裝程式會提示，並提供 `templates/pre-commit-block.yaml` |
| 原本沒有以換行結尾的 CLAUDE.md、AGENTS.md，移除後會多一個換行 | 影響很小 |
| `.claude/settings.json` 安裝後會重新排版 | 內容不變；移除後內容一致，但排版可能不同 |
| skill 可能沒有被觸發 | 違規訊息會指向對應的 skill；START.md 也適用於沒有 skill 的 AI 工具 |
| Codex 沒有 Read 工具，各層規則在第一次編輯該層時才附上：第一次編輯是在沒看到規則的情況下寫的 | post-edit 會立刻抓可檢查的違規；常駐規則有寫「改到哪一層照哪一層的規則」 |
| Codex 的 hook 要被使用者信任過才會執行，AIR 無法從外部確認 | 安裝輸出與 doctor 都提醒；commit 前檢查不受影響 |
| 沒有 session_id 的宿主，注入紀錄共用 `unknown`，規則只附一次直到下次 session 開始 | 目前支援的宿主都有 session_id |
| Claude Code 每次 Read 多啟動一個 Python 行程（Linux 約 0.1 秒，Windows 實測約 0.36 秒） | 讀檔前只查層與紀錄，不做 AST。改用 Claude Code 內建的 `.claude/rules` 路徑範圍規則可以不啟動 Python，列在待決事項 |
| 跨宿主的 hook 合約只用 fixture 測試，沒有用宿主的 JSON Schema 驗證 | Codex 的 schema 在它的 repo，之後再接 |
| 語意審查由改程式的同一個 AI 做時有自評偏差；程式只能驗證格式、範圍與一致性，驗證不了判斷對不對 | skill 預設自己審，待審檔案多或使用者要求時才交給子 agent（用 `--bundle` 貼給它）；結果是參考，不是驗收。誤判率沒有在真實 session 量測過 |
| 「這次變更引入」只能用行號是否落在改到的行附近判斷（±3 行） | 改動引發的問題在別處時，審查者要把行號指到改到的行；新檔案整個檔案都算範圍 |
| 審查紀錄（`.air/review.json`）跟驗收紀錄一樣是本機的工作紀錄，可以被改 | 可信的關卡在 CI 重做；`verify` 不依賴審查紀錄 |
| 深度學習專案的模型、損失、訓練迴圈都依賴框架，全部落在 adapters；steps 只剩前後處理與 numpy 版指標 | 刻意的取捨：steps 不碰框架，測試才快、才檢查得了。專案要讓張量跨層時，經同意加進 `imports.extra`（CTR-4、ADP-2） |
| Dataset 從磁碟串流大資料集時，讀檔發生在 adapters，不在 storage | 範例 `trainer.md` 給的做法：Dataset 只拿路徑清單，逐筆讀取交給 contracts 的 Protocol、storage 實作、main 注入。沒有程式檢查，靠審查 |
| `pause` 是指令，AI 也跑得動，程式分不出是誰執行的 | START.md 與 AGENTS.md 寫明只由使用者執行；每次都記進 `history.jsonl`、`status` 顯示原因，事後看得出來 |
| 增量審查看不到間接影響：A 改了讓既有的 B 不合規，B 內容沒變就不重審 | 跨檔的依賴方向與 import 由全專案的程式檢查抓；審查只管程式抓不到的部分。要重審 B 時改一下它就會重新列入 |

## 6. 待決事項

| 事項 | 現況與建議 |
|---|---|
| **是否採用 Kedro** | 建議暫不採用，但保持相容。steps 已經符合 Kedro 對 node「純函式、不碰 I/O」的要求。主要衝突是：Kedro 的 pipeline 是宣告式的，「呼叫外部工具」會落在 node 裡，跟「Protocol 由 flows 呼叫」的設計不合。Kedro 1.7 會帶進 39 個依賴，而且遙測預設開啟，也與零依賴的方向相反。重新評估的時機：資料來源超過 3 到 5 個、需要追蹤資料版本、需要並行執行，或開始多人合作時。 |
| 實測依位置載入規則 | 在互動模式下讓 AI 編輯某一層的檔案，再用 `/memory` 確認該層規則有被載入 |
| 實際專案的遷移試跑 | 目前只用 AIR-dev 裡的範例專案測過安裝與檢查；分析、計畫、逐批遷移的流程還沒有在真實專案上跑過。2026-10-23 的實戰檢討報告（AICUP_2026）列出了多 session、研究型專案的測試、token 放大器等問題，分批處理中 |
| 保護型 hook 壞掉時要不要擋 | 編輯前、Bash 前的 hook 可以對 Claude Code 設 `onFailure: "block"`（2.1.295 起）：hook 自己壞掉就擋下，而不是放行。代價是 Python 壞掉時所有編輯都被擋；`doctor` 的冒煙測試能先抓到 |
| Windows 沒有 Git Bash 時 | Claude Code 會改用 PowerShell 執行 hook，AIR 的 sh 腳本無法執行；目前只在文件寫明需要 Git for Windows，`doctor` 會指出找不到 sh |

## 7. 學到的事

1. **寫規則的人最容易違反規則。** 數量上限、標記要誠實、規則只有一個來源，這幾條原則在修改規範的過程中都被違反過，最後是靠實測和重新清點才抓出來。
2. **實測比推理可靠。** 很多問題都是實際跑過才發現：ruff 的某些禁用沒有效果、shell 版本不同造成亂碼、軟規則讓 commit 失敗、套件在使用者專案裡留下快取檔。
3. **「沒報錯」會被當成「合規」。** 標記必須誠實，常駐規則裡也要明說檢查只涵蓋一部分。
4. **黑名單依賴記憶，白名單依賴機制。** 需要 AI「記得」去做的事都不可靠。
5. **用詞會改變 AI 的行為。** 「擋下」和「已寫入、必須修正」只差幾個字，但前者可能讓 AI 以為檔案沒有被修改。
6. **範例也是規則。** AI 會模仿範例；範例違反規則，比沒有範例更糟。
7. **軟規則一旦會擋，就會造成過度拆分。** 所以軟規則必須在每一道關卡都只提醒。
8. **反駁之前先查證。** 曾經判斷外部意見是錯的，查了官方文件才發現錯的是自己，還白做了一整套跟內建功能重複的機制。
9. **外部意見也要逐條檢驗。** 接受建議的方向，但要驗證細節。
10. **結構問題不要只修症狀。** 把 Protocol 移到正確的層之後，規則才從靠自律變成可以檢查。
11. **檢查工具要先有測試，再擴充；測試也要驗證自己。** 一次全部通過的測試要故意改壞程式，確認它真的會失敗。
12. **能用內建機制，就不要自己做。** 自建的狀態可能跟平台的實際狀態不同步。
13. **提交前先看清楚要提交什麼。** commit 前的檢查只檢查程式碼有沒有違規，不會檢查某個檔案該不該提交。
14. **自己的防護也會擋到自己。** 改造規範時，舊的 hook 擋下了解除安裝 pre-commit 的指令。正確的做法是換一條正當的路，而不是想辦法繞過防護。
15. **要放進別人專案的東西，假設越少越好。** 寫死的路徑、套件名稱、工具依賴、內嵌的 `.git`、機器專屬的路徑，在「新專案」裡都不是問題，到了「別人的專案」全都會出問題。
16. **實戰平台不是開發平台。** 在 ubuntu 全綠的強制機制，到 zh-TW Windows 會因為編碼、找不到 Python、結束碼被放行而整個靜默失效，而且沒有人收到通知。CI 要跑實戰的平台與語系；fail-open 一定要留痕跡。
