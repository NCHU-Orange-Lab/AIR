# AIR 設計說明

> 給維護這套規範的人：說明為什麼這樣設計、目前有哪些設計決定與限制，以及設計過程中學到的事。
> 設計決定只列出現行的版本；之後有變更時，直接改寫第 4 節。

---

## 1. 目的

1. **流程與步驟分開**：步驟是純函式，流程只負責串接，I/O 交給最外層（函式式核心、命令式外殼）。
2. **讓 AI 遵守得了**：不一次給 AI 全部規則，只給跟它當下工作有關的少量規則。
3. **能檢查的就用程式強制**，不能檢查的才靠文字和 AI 的判斷。
4. **能接入第三方工具**（例如 YOLO），又不破壞分層。
5. **能重複用在很多專案**：把資料夾放進既有專案，AI 就能照著把專案重構成這個架構。

---

## 2. 設計原則

1. **規則依時機分批送給 AI**：常駐、依位置、依任務、違規當下。
2. **能機械判斷的交給程式，需要判斷力的交給 AI**：程式負責檢查，skills 負責教做法和判斷標準。
3. **規則內容只有一個來源**：`AIR/config.toml`；所有腳本只負責執行。
4. **軟規則只提醒，不擋**：函式長度、複雜度在任何關卡都不會造成失敗，避免 AI 為了過關而過度拆分。
5. **預設禁止**：純的層採用 import 白名單，不用黑名單。
6. **標記要誠實**：只能檢查到一部分的規則，要標〔hook 部分檢查〕並舉出抓不到的例子。
7. **規則數量有上限**：常駐 3 條、每層最多 6 條、每個 skill 約 60 行。
8. **檢查工具本身也要有測試**：測試跟著套件走（`AIR/tests/`），只用標準庫，任何環境都能跑。
9. **能用平台的內建機制，就不要自己做**。
10. **套件不能污染專案**：不覆蓋不是自己建立的東西；可以重複安裝；移除後還原原本的檔案；不留下快取或機器專屬的檔案。
11. **重構既有專案要分階段、可以喊停**：每個階段都停下來等使用者核准，一批一個 commit。

---

## 3. 運作方式

### 套件與專案的分界

```
AIR/              套件：更新時整包換掉，專案裡不修改
.air/             專案設定：更新時保留
接點              CLAUDE.md、AGENTS.md、.claude/、commit 前檢查、各層的 CLAUDE.md
                  —— 全部由 install.sh 建立、uninstall.sh 移除
```

### 規則如何送到 AI 面前

| 時機 | 機制 |
|---|---|
| 每次對話 | 專案的 `CLAUDE.md` 用 `@AIR/AGENTS.md` 匯入常駐規則；其他 AI 工具透過專案的 `AGENTS.md` 得到指引 |
| 進入某一層 | Claude Code 內建：讀寫某目錄的檔案時，自動載入該目錄的 `CLAUDE.md`（對話壓縮後也會重新載入） |
| 做某種任務 | skills（`.claude/skills/air-*`） |
| 違規當下 | 檢查訊息帶規則編號與修法 |

### 檢查

單一指令 `air.py check` 負責所有規則（AIR000–AIR008、AIR101–AIR102），由四道關卡呼叫：編輯後、執行 Bash 前（擋下略過檢查的指令）、結束前、commit 前。只檢查層內的程式；舊程式碼不檢查，所以遷移到一半時專案仍可以正常 commit。

## 4. 主要設計決定

| 決定 | 理由 |
|---|---|
| 做成可以放進專案根目錄的資料夾，大部分內容留在 `AIR/` 裡 | 更新時整包替換即可；專案根目錄只增加少量、可以完整移除的接點 |
| 不使用 copier 等範本工具 | 整包替換加上可重複執行的 install.sh，就能做到更新；少一個依賴 |
| 套件裡不能有 `.git`；開發 repo（AIR-dev）與套件（`AIR-dev/AIR/`）分開 | 內嵌的 `.git` 會讓專案的 git 不追蹤套件內容 |
| 啟動方式是對 AI 說「照 AIR/START.md 安裝」 | Claude Code 不會自動讀取子資料夾的規則，至少需要一個啟動動作；用一句話啟動，任何 AI 工具都能用 |
| 專案設定放在 `.air/`，不放在 `AIR/` 裡 | 更新時整包替換套件，專案設定才不會遺失 |
| `.air/python` 不進版本控制 | 路徑因機器而異；每個 clone 都要執行一次 install.sh（git hook 本來就需要） |
| 零依賴：只需要 Python 3.11+ | 不干擾專案原本的工具與環境（poetry、uv、conda、沒有 pre-commit 的專案） |
| 所有檢查收進自寫的 `air.py`，取代 ruff、import-linter | 零依賴；分層方向從「結束前才檢查」變成「每次編輯就檢查」；一套設定、一套測試 |
| 用名稱比對與別名解析，不做型別推論 | `to_csv`、`sample` 這類規則不需要知道型別；代價是會擋到同名但無害的方法 |
| 「舊程式碼區」取代違規基準線 | 只檢查層內的程式，舊程式碼照常運作；層對舊模組的依賴要明確列在 allow-legacy，並寫上原因 |
| 遷移分 6 個階段，每個階段停下來等核准 | 分類需要判斷力，重構有風險；每批先補行為保護測試，一批一個 commit，隨時可以回退 |
| 遷移期間在舊模組保留轉接，收尾時再移除 | 呼叫端不用一次全改，每一批都能保持專案可以執行 |
| 分成六層，最底層是 contracts | Protocol 如果放在 steps，steps 就擁有一個自己不准用的東西，外層也被迫依賴 steps |
| 只有 flows 能呼叫 Protocol | steps 才能維持純函式，而且可以檢查 |
| flows 可以呼叫子流程，但不能循環 | 大流程由小流程組成很常見 |
| storage 的規則前綴維持 `IO` | 規則編號一旦用過就不改 |
| 套件產生的檔案都加上標記（`AIR:MANAGED`、`.air-managed`、標記區塊） | 安裝與移除只動自己的東西 |
| 新建 `CLAUDE.md` 時，若專案原本有 `AGENTS.md`，就一併匯入 | 有了 CLAUDE.md 之後，Claude Code 就不會再讀 AGENTS.md |
| 用 shlex 解析指令，判斷是否在略過 commit 前的檢查 | 正規表示式會誤判 commit 訊息裡的文字 |
| 專案定位是通用資料處理，文件使用繁體中文 | YOLO 只當作第三方工具的範例 |

## 5. 已知限制

| 限制 | 目前的處理 |
|---|---|
| 只支援 Python 專案 | START.md 的前置檢查會停下來告知 |
| 沒有無法略過的關卡（沒有 CI＋分支保護） | commit 前檢查可以被人手動略過；有遠端儲存庫時再加 CI |
| 每個 clone 都要執行一次 install.sh | 寫在 README；`.air/python` 與 git hook 都不進版本控制 |
| pre-bash hook 判斷不到腳本檔（`sh run.sh`）或變數展開裡的指令（`bash -c "..."` 會拆開，最多三層） | 盡力而為；權威的關卡是 commit 前檢查 |
| 沒有型別標註、直接傳進 steps 的工具物件抓不到 | STEP-2 標為〔部分〕 |
| 其他函式庫自己的取時間、取亂數方法 | STEP-3 標為〔部分〕；需要時加進 `banned-calls` 或 `required-args` |
| 方法名稱比對會擋到同名但無害的方法 | 刻意的取捨 |
| 函式長度、複雜度是粗略計算 | 只用於提醒 |
| `.pre-commit-config.yaml` 的 `repos:` 不是最後一個頂層設定時，無法自動加入 | 安裝程式會提示，並提供 `templates/pre-commit-block.yaml` |
| 原本沒有以換行結尾的 CLAUDE.md、AGENTS.md，移除後會多一個換行 | 影響很小 |
| `.claude/settings.json` 安裝後會重新排版 | 內容不變；移除後內容一致，但排版可能不同 |
| skill 可能沒有被觸發 | 違規訊息會指向對應的 skill；START.md 也適用於沒有 skill 的 AI 工具 |
| 依位置載入規則沒有在互動模式下實測 | 依據是官方文件 |

## 6. 待決事項

| 事項 | 現況與建議 |
|---|---|
| **是否採用 Kedro** | 建議暫不採用，但保持相容。steps 已經符合 Kedro 對 node「純函式、不碰 I/O」的要求。主要衝突是：Kedro 的 pipeline 是宣告式的，「呼叫外部工具」會落在 node 裡，跟「只有 flow 能呼叫 Protocol」的設計不合。Kedro 1.7 會帶進 39 個依賴，而且遙測預設開啟，也與零依賴的方向相反。重新評估的時機：資料來源超過 3 到 5 個、需要追蹤資料版本、需要並行執行，或開始多人合作時。 |
| 實測依位置載入規則 | 在互動模式下讓 AI 編輯某一層的檔案，再用 `/memory` 確認該層規則有被載入 |
| 實際專案的遷移試跑 | 目前只用 AIR-dev 裡的範例專案測過安裝與檢查；分析、計畫、逐批遷移的流程還沒有在真實專案上跑過 |
| CI | 有遠端儲存庫時，加上 CI 與分支保護 |

## 7. 學到的事

1. **寫規則的人最容易違反規則。** 數量上限、標記要誠實、規則只有一個來源，這幾條原則在修改規範的過程中都被違反過，最後是靠實測和重新清點才抓出來。
2. **實測比推理可靠。** 很多問題都是實際跑過才發現：ruff 的某些禁用沒有效果、shell 版本不同造成亂碼、軟規則讓 commit 失敗、套件在使用者專案裡留下快取檔。
3. **「沒報錯」會被當成「合規」。** 標記必須誠實，常駐規則裡也要明說檢查只涵蓋一部分。
4. **黑名單依賴記憶，白名單依賴機制。** 需要 AI「記得」去做的事都不可靠。
5. **用詞會改變 AI 的行為。** 「擋下」和「已寫入、必須修正」只差幾個字，但前者可能讓 AI 以為檔案沒有被修改。
6. **範例也是規則。** AI 會模仿範例；範例違反規則，比沒有範例更糟。
7. **軟規則一旦會擋，就會造成過度拆分。** 所以軟規則必須在每一道關卡都只提醒。
8. **反駁之前先查證。** 曾經判斷外部意見是錯的，查了官方文件才發現錯的是自己，還白做了一整套跟內建功能重複的機制。
9. **外部意見也要逐條檢驗。** 接受建議的方向，但要驗證細節。
10. **結構問題不要只修症狀。** 把 Protocol 移到正確的層之後，規則才從靠自律變成可以檢查。
11. **檢查工具要先有測試，再擴充；測試也要驗證自己。** 一次全部通過的測試要故意改壞程式，確認它真的會失敗。
12. **能用內建機制，就不要自己做。** 自建的狀態可能跟平台的實際狀態不同步。
13. **提交前先看清楚要提交什麼。** commit 前的檢查只檢查程式碼有沒有違規，不會檢查某個檔案該不該提交。
14. **自己的防護也會擋到自己。** 改造規範時，舊的 hook 擋下了解除安裝 pre-commit 的指令。正確的做法是換一條正當的路，而不是想辦法繞過防護。
15. **要放進別人專案的東西，假設越少越好。** 寫死的路徑、套件名稱、工具依賴、內嵌的 `.git`、機器專屬的路徑，在「新專案」裡都不是問題，到了「別人的專案」全都會出問題。
